## 1. Problem Statement

An endpoint in `EndpointState.QUARANTINED` or `RECOVERY_REQUIRED` lacks trustworthy evidence that the physical endpoint is safe. The M49.3.5 recovery protocol establishes an explicit, generation-bound, physically-fenced, and concurrently-safe architecture to recover these endpoints, eliminating all process-restart and concurrency ambiguities.

## 3. Authority Model

### 3.1 Durable Cross-Process Authority Boundary

The architecture explicitly defines a durable cross-process authority boundary (`AuthoritativeRecoveryRecord` or equivalent durable store) to atomically commit the final recovery state. Local Python fields are NOT the authoritative source for cross-process final state.

- **`AuthoritativeRecoveryRecord` (Durable Authority)**: Persists the explicit independent durable dimensions. No normative operation may require a field that the durable authoritative record does not persist. Explicitly, it contains:
  - **Immutable recovery identity:** `authorization_id`, `recovery_id`, `physical_operation_id`, `endpoint_id`, `device_id`, `lifecycle_generation`
  - **Immutable / generation-bound epoch identity:** `quiescence_authority_epoch`, `operation_fencing_epoch`, `recovery_authorization_epoch`
  - **Physical termination authority:** 
    Persisted as part of the terminal physical transition. It is immutable after accepted reconciliation or finalization. It is strictly evidence-bound to the exact termination proof metadata or authoritative reference required for reconstruction, not merely the "latest epoch seen". Duplicate reconciliation reads this bound proof to idempotently confirm status. Restart uses it to deterministically reconstruct the validated termination fact.
  - **Mutable lifecycle state:**
    - `transaction_state`: Allowed values: `PENDING`, `SUCCESSFULLY_FINALIZED`, `FAILED`, `INVALIDATED`
    - `protocol_state`: Allowed values: `NONE`, `RECOVERY_IN_PROGRESS`, `RECOVERY_FAILED`, `RECOVERY_CONFIRMED`
    - `physical_operation_state`: Allowed values: `ACTIVE`, `TERMINATION_PENDING`, `TERMINATED_AND_PROVEN`
    - `physical_ownership`: Allowed values: `RETAINED`, `RELEASED`
    - `endpoint_state`: Allowed values: `QUARANTINED`, `RECOVERY_REQUIRED`, `READY`
  - **Execution reconciliation metadata:** Preserves the existing execution-reconciliation contract.

  The exact lifecycle must be mechanically explicit. For example, after a protocol timeout:
  ```text
  transaction_state = FAILED
  physical_operation_state = TERMINATION_PENDING
  physical_ownership = RETAINED
  protocol_state = FAILED
  endpoint_state != READY
  ```
  Then, after authoritative late termination (Physical Operation Reconciliation):
  ```text
  transaction_state = FAILED
  physical_operation_state = TERMINATED_AND_PROVEN
  physical_ownership = RELEASED
  protocol_state = FAILED
  endpoint_state != READY
  ```
  This second state is legal and terminal. `FAILED` protocol state does NOT imply `physical ownership released`.
- **`RecoveryCoordinator` (Local Projection)**: A local projection/cache of the durable authority. After a restart, the local projection MUST be reconstructed from authoritative state. It cannot infer final state from missing in-memory variables.
- **Physical Operation Lifecycle**: Physical operations exist independently of protocol success/failure (`ACTIVE` → `TERMINATION_PENDING` → `TERMINATED_AND_PROVEN`). This guarantees that a protocol timeout does not erase unresolved physical ownership tracking.

| Responsibility | Sole Authority |
|---|---|
| Hardware Fencing Authority | Hardware Monotonic Fencing Epoch |
| Proving Physical Quiescence | Hardware response to Epoch-bound Abort Command (`QuiescenceConfirmation`) |
| Tracking physical ownership | `AuthoritativeRecoveryRecord` (Durable), projected locally via `RecoveryCoordinator` |
| Tracking protocol attempt | `AuthoritativeRecoveryRecord` (Durable), projected locally via `RecoveryCoordinator` |
| Asserting Physical Termination Fact (PATH A) | `TerminationConfirmation` + Epoch/Spatial/Authorization Validation + `driver_authority_proof` |
| Asserting Physical Termination Fact (PATH B) | `TerminationConfirmation` + Epoch/Spatial/Operation Validation + `driver_authority_proof` |
| Asserting Recovery Safety Evidence | `RecoveryConfirmation.safety_evidence_valid` |
| Authorizing `→ IDLE` (Recovery-finalization ownership release) | `AUTHORITATIVE_FINALIZE` stored in `AuthoritativeRecoveryRecord` |
| Authorizing `→ IDLE` (Failed/timed-out physical-operation ownership release) | `AUTHORITATIVE_RECONCILE_TERMINATION` stored in `AuthoritativeRecoveryRecord` |
| Authorizing `→ READY` (Endpoint State) | `AUTHORITATIVE_FINALIZE` ONLY stored in `AuthoritativeRecoveryRecord` |

## 4. Endpoint States

- **`QUARANTINED`**: Physical uncertainty exists due to execution failure (`FAULTED_UNKNOWN` or `INTERLOCKED`).
- **`RECOVERY_REQUIRED`**: Physical uncertainty exists due to software initialization / process restart.

**Shared Rule:** Both strictly block command admission and execution claims. Neither may become `READY` except through successful fenced physical recovery.

---

## 5. Recovery Protocol State Machine (Software Intent)

- **`NONE`**: No active protocol.
- **`RECOVERY_IN_PROGRESS`**: Request admitted, timeout ticking.
- **`RECOVERY_FAILED`**: Timeout expired, identity mismatch, or safety rejected. Protocol is immutable metadata.
- **`RECOVERY_CONFIRMED`**: `READY` transition successful.

## 6. Fencing Model & Quiescence Authority

Process restart wipes in-memory ownership. A starting process has NO KNOWLEDGE of whether the hardware is physically executing OP-A from a dead Process A.

### 6.1 Fencing Epoch and Quiescence Confirmation Contract
The driver and hardware interface MUST enforce a **Monotonically Increasing Fencing Epoch**. To establish physical quiescence, the system MUST validate an explicit authoritative `QuiescenceConfirmation` contract.

**QuiescenceConfirmation Contract MUST contain:**
- `endpoint_id`
- `device_id`
- `fencing_epoch`
- `hardware_state` (idle/quiescent state)
- `stale_operations_state` (authoritative indication that stale physical operations are terminated or proven absent)
- `driver_authority_proof` (explicit verifiable proof from the authoritative driver/hardware)

The architecture specifies that `identity != proof`. An arbitrary callback/source cannot manufacture a valid quiescence authority proof. The proof MUST authenticate the exact quiescence assertion for the current fencing epoch.

**Exact Fencing Transition:**
1. `FENCING_REQUIRED`
2. → `LEASE_ACQUIRED(E)`: A new process acquires a new epoch `E` from the hardware. Hardware atomically updates its epoch to `E` and rejects commands with `< E`.
3. → `ABORTING_STALE_OPERATIONS(E)`: Driver issues an abort command under epoch `E`.
4. → receive `QuiescenceConfirmation`
5. → validate `endpoint_id`
6. → validate `device_id`
7. → validate `fencing_epoch` == current authoritative epoch `E`
8. → validate `hardware_state` == IDLE/QUIESCENT
9. → validate `stale_operations_state` == TERMINATED/PROVEN ABSENT
10. → validate `driver_authority_proof`: missing, malformed, invalid, stale-epoch, wrong-spatial, or non-authenticating proofs MUST BE REJECTED.
11. → only then enter `PHYSICALLY_QUIESCENT(E)`.

**Stale Quiescence, Notification & Invalidation Trigger:**
`PHYSICALLY_QUIESCENT(E)` is a process-local state tracking an underlying hardware reality. A local process MUST NOT interpret an old quiescence confirmation as permanently valid.
1. `PHYSICALLY_QUIESCENT(E1)` established by Process A.
2. → `E1` invalidated by `E2` (hardware epoch advances).
3. If Process A observes the invalidation: Local state becomes `QUIESCENCE_STALE(E1)`.
4. If Process A receives NO notification: `LocalQuiescenceState` remains `PHYSICALLY_QUIESCENT(E1)`, BUT `EffectiveQuiescenceAuthority` is instantly `NONE` at the hardware boundary.
5. → Physical dispatch under `E1` is explicitly PROHIBITED and will be rejected by the hardware regardless of `LocalQuiescenceState`.
6. → Coordinator MUST enter a deterministic recovery/re-fence path. Fresh `E2` fencing/quiescence is required.

### 6.2 Process Death During Fencing (Model A)
Process death during fencing leaves physical state UNKNOWN. Under Model A semantics, **process death does NOT imply epoch invalidation**. The hardware continues executing operations under the dead process's epoch until explicitly superseded by a successor epoch.
If Process A acquires `E1` and dies before reaching `PHYSICALLY_QUIESCENT`, Process B may request/attempt a new recovery protocol, BUT physical recovery dispatch remains strictly prohibited until:
1. fresh fencing epoch `E2` is acquired;
2. `E1` is invalidated by the hardware;
3. stale physical operations are aborted/proven absent under `E2`;
4. an authoritative `QuiescenceConfirmation` bound to `E2` is validated;
5. `PHYSICALLY_QUIESCENT(E2)` is established;
6. recovery dispatch is bound to `E2`.

### 6.3 Dispatch-Epoch Binding
The `RecoveryCoordinator` MUST explicitly bind the physical recovery dispatch to the exact epoch that established quiescence. `execute_recovery(OP-B)` must be executed under `E_new`. Before dispatching, the coordinator MUST pass through an explicit current-epoch gate verifying `E_new` is still authoritative. If `E_new` is stale, dispatch fails safely.

### 6.4 Effective vs Local Ownership and Hardware Fencing Authority
Hardware fencing authority is authoritative independently of whether the old process has learned about invalidation. After `E1` is invalidated by authoritative `E2`, Process A/`E1` has ZERO effective physical authority.

**Exact Legal Transitions:**

**Scenario A (Observed Invalidation):**
1. `ACTIVE(E1)`
2. → `E1 invalidated by E2`
3. → Local process A receives authoritative notification of fencing.
4. → Local state becomes `FENCING_INVALIDATED`. Process A drops all tracking; effective physical authority is NONE.

**Scenario B (Unnotified Invalidation):**
1. `ACTIVE(E1)`
2. → `E1 invalidated by E2`
3. → No notification received.
4. → Local state may remain stale in memory (reads as `ACTIVE`).
5. → BUT effective physical authority = NONE.
6. → No physical command, retry, release, or READY transition is permitted by Process A under `E1`. Hardware rejects all attempts.

The hardware epoch is the absolute source of truth. Stale local bookkeeping MUST NOT be interpreted as current physical ownership. Process A cannot release `E2` ownership, and a callback from `E1` after invalidation cannot mutate `E2` state.

### 6.5 Formal Separation of Four Epoch Concepts
A newer authoritative fencing epoch can authoritatively terminate or prove termination of operations dispatched under an older, invalidated epoch. To ensure complete correctness in a multi-epoch recovery sequence, the architecture formally separates four distinct epoch concepts:

1. **`quiescence_authority_epoch`**: The epoch under which hardware/driver physical quiescence is established and maintained BEFORE physical dispatch.
2. **`operation_fencing_epoch`**: The immutable epoch under which a physical operation was originally dispatched. (At dispatch time, this MUST equal the current `quiescence_authority_epoch`).
3. **`termination_authority_epoch`**: The epoch whose hardware/driver authority establishes that a specific physical operation has definitively terminated.
4. **`recovery_authorization_epoch`**: The epoch under which the final Recovery Authorization (READY transition) is committed.

**Cross-Epoch Enforcement Logic:**
The durable record MUST explicitly persist `quiescence_authority_epoch`, `operation_fencing_epoch`, and `recovery_authorization_epoch` as generation-bound/immutable fields for a specific recovery authorization.

When the active PATH A recovery authorization is established and physical dispatch is authorized:
```text
quiescence_authority_epoch == operation_fencing_epoch == recovery_authorization_epoch
```
For valid physical termination evidence:
```text
termination_authority_epoch >= operation_fencing_epoch
```
PATH A MUST require at finalization linearization:
```text
termination_authority_epoch == recovery_authorization_epoch == current authoritative hardware epoch
```
PATH B MAY use:
```text
operation_fencing_epoch = E1
termination_authority_epoch = E2
```
with no READY consequence.

- **AUTHORITATIVE_RECONCILE_TERMINATION (PATH B)** MUST enforce that the `termination_authority_epoch` matches the current authoritative hardware epoch.

## 7. Physical Operation State Machine (Process-Local vs Effective)

**Process-Local Operation State (Bookkeeping):**
- **`IDLE`**: No physical operation tracking is active in this process.
- **`ACTIVE`**: Local dispatch tracking is active.
- **`FENCING_INVALIDATED`**: Terminal state indicating the process observed that its fencing epoch was invalidated; the operation tracking is dead.

**Effective Physical Authority (Hardware State):**
- **Valid (`E`)**: The epoch `E` matches the current hardware fencing authority.
- **`NONE`**: The hardware epoch has advanced past this operation's epoch. The operation holds ZERO effective physical authority, regardless of its local `ACTIVE` status.

## 9. Dispatch Model, Timeout & Post-Timeout Lifecycle

### 9.1 Executor Submission and Failure
1. Assert hardware is NOT in physical recovery mode.
2. Submit operation to executor.
3. Hand off physical recovery operation.
4. If `SUBMISSION_REJECTED_BEFORE_ACCEPTANCE` occurs: clear `active_physical_operation_id` (since it never started), Protocol becomes `FAILED`. No physical termination callback is expected. (Note: If `EXECUTION_FAILED_AFTER_ACCEPTANCE` occurs, physical operation ownership = `RETAINED` until authoritative termination is resolved).

### 9.2 Early or Invalid Callback Mitigation
If an executor callback arrives *before* the physical operation completes Phase 1 setup, or fails identity matching (e.g., mismatched `physical_operation_id` or `authorization_id` depending on the path), it is an **early / invalid callback**.
**Required Semantic:** 
- Reject callback.
- Protocol state = Unchanged.
- Physical ownership = Retained.
- NO `READY` transition.

## 10. Callback Validation & Authoritative Termination Confirmation

A callback asserting termination MUST provide a `TerminationConfirmation` contract explicitly issued by valid current hardware/driver authority. It cannot merely be a structurally valid payload containing `TERMINATED_AND_FINAL`.

The architecture specifies that an identity string is NOT proof of authority. The confirmation MUST contain a verifiable `driver_authority_proof` that the coordinator can validate against the current authoritative fencing epoch / hardware authority. Identity != Proof. An arbitrary callback producer cannot manufacture an accepted authority proof. Missing, malformed, expired, wrong-epoch, wrong-operation, or stale-authority proofs result in rejection.

**RecoveryTerminationConfirmation (PATH A):**
- `physical_operation_id`
- `recovery_id`
- `endpoint_id`
- `device_id`
- `lifecycle_generation`
- `operation_fencing_epoch`
- `termination_authority_epoch`
- `driver_authority_proof`
- `termination_state` (authoritative-final indication)

**PhysicalTerminationReconciliationConfirmation (PATH B):**
- `physical_operation_id`
- `endpoint_id`
- `device_id`
- `lifecycle_generation`
- `operation_fencing_epoch`
- `termination_authority_epoch`
- `driver_authority_proof`
- `termination_state` (authoritative-final indication)

**Cross-Epoch Termination Cases:**
- **CASE A:** OP-A created under E1 and terminates while E1 is authoritative. `operation_fencing_epoch = E1`, `termination_authority_epoch = E1`. Valid.
- **CASE B:** OP-A created under E1. E2 invalidates E1. E2 authoritatively aborts/proves OP-A terminated. `operation_fencing_epoch = E1`, `termination_authority_epoch = E2`. Valid, provided E2 is current authoritative termination authority and all operation identities match.
- **CASE C:** Stale E1 authority attempts to assert OP-A termination after E2. Reject. E1 is no longer authoritative.
- **CASE D:** E2 claims termination of unrelated physical operation. Reject due to exact `physical_operation_id` binding.
- **CASE E:** E2 claims termination but cannot provide authoritative proof that OP-A actually terminated. Reject; ownership remains retained.

### 10.1 The Unified Authority Boundary

The architecture defines ONE abstract authority boundary: `UnifiedAuthority`.
`UnifiedAuthority` is the sole abstract linearization boundary for:

1. `ACQUIRE_FENCING_EPOCH`
2. `AUTHORITATIVE_FINALIZE`
3. `AUTHORITATIVE_RECONCILE_TERMINATION`

All three operations participate in the same authoritative total-order model. The concrete implementation technology may remain abstract, but the `UnifiedAuthority` MUST provide this exact ordering guarantee and ensure hardware authority and durable authority cannot permanently disagree. The abstract contract MUST specify:
1. what constitutes linearization;
2. what state exists before linearization;
3. what state exists after linearization;
4. how a crash between external effects is resolved;
5. which source wins for each observable combination;
6. how impossible combinations fail safe.
The authority boundary cannot merely assert “one total order”; it must define enough semantics for an implementation to be mechanically derived.

**The Unified Authority primitives:**

The `UnifiedAuthority` MUST use an abstract authority-transition record to make crash recovery non-circular. This record includes at minimum:
- `authority_transition_id`
- `transition_type`
- `target_identity`
- `requested_epoch`
- `previous_epoch`
- `durable_transition_state`
- `linearization_outcome`
- `hardware_observation`
- `durable_observation`

Where `target_identity` is explicitly bound according to the transition:

### ACQUIRE_FENCING_EPOCH
Bind:
- endpoint/device identity
- requested epoch
- previous epoch

### AUTHORITATIVE_FINALIZE
Bind:
- authorization_id
- recovery_id
- physical_operation_id
- endpoint_id
- device_id
- lifecycle_generation
- recovery_authorization_epoch

### AUTHORITATIVE_RECONCILE_TERMINATION
Bind:
- physical_operation_id
- endpoint_id
- device_id
- lifecycle_generation
- operation_fencing_epoch
- termination_authority_epoch

A crash recovery process MUST be able to determine exactly WHICH operation/authorization the transition refers to.

#### 1. `ACQUIRE_FENCING_EPOCH(E_new)`
- **Preconditions:** Caller holds identity validation to request epoch advancement.
- **Hardware epoch transition:** Updates the single authoritative hardware epoch to `E_new`.
- **Durable invalidation:** Automatically makes older `PENDING` authorizations durably `INVALIDATED` or immediately ineligible.
- **Before linearization:** Neither operation is authoritative. The transition state is `PENDING`.
- **After linearization:** The exact result is authoritative. The transition state is `COMMITTED` (success) or `ABORTED` (failure).
- **Crash with local outcome UNKNOWN:**
  The architecture defines an exact mechanically decidable resolution table:
  - **State A:** Transition `PENDING`, hardware still E1. Result: transition did not linearize; E1 remains authoritative; no PENDING authorization invalidation.
  - **State B:** Transition `PENDING`, hardware already E2. Result: transition DID linearize or otherwise has a deterministically committed hardware outcome; E2 becomes authoritative; old PENDING authorizations are invalidated/ineligible; durable transition record MUST converge to the committed outcome before successor operations proceed.
  - **State C:** Transition `COMMITTED`, hardware E2. Result: E2 authoritative.
  - **State D:** Transition `ABORTED`, hardware E1. Result: E1 authoritative.
  - **State E:** Logically impossible combinations (e.g. COMMITTED but hardware E1) MUST be explicitly identified as an integrity fault that fails safe and blocks READY/dispatch until reconciled.
  Do NOT say `PENDING -> old epoch` without observing and reconciling the actual hardware state.

#### 2. `AUTHORITATIVE_FINALIZE(recovery_transition, expected_recovery_authorization_epoch)`
The unified authority serializes finalization. It observes the current authoritative hardware epoch and durable recovery record within ONE defined linearization boundary.
It succeeds ONLY if:
1. `expected_recovery_authorization_epoch == durable.recovery_authorization_epoch`
2. `expected_recovery_authorization_epoch == current authoritative hardware epoch`
3. `recovery_transition.termination_authority_epoch == expected_recovery_authorization_epoch`
4. Authorization state is still `PENDING`.
5. All identity bindings match.
6. Termination proof is valid.
7. Safety evidence is valid.

**Crash Semantics:**
1. **Before finalization linearization:** Transition is PENDING. Durable recovery record is unchanged. Transaction remains `PENDING`.
2. **After finalization linearization:** Transition is COMMITTED. Final state is `SUCCESSFULLY_FINALIZED`, `TERMINATED_AND_PROVEN`, `RELEASED`, `READY`, `CONFIRMED`.
3. **Transition record PENDING + local UNKNOWN:** Restart reconstructs exact state from authoritative durable record.
4. **Transition record COMMITTED (Projection/state reconciliation after already-committed authority):** The authoritative transition has already linearized; restart MUST NOT create a second authority transition. Restart reconstructs the committed authoritative state. Any missing local/durable projection is repaired idempotently from that already-committed authority. Repair MUST NOT permit partial ownership release, MUST NOT convert an uncommitted transition into committed, and MUST NOT create READY unless the authoritative committed PATH A state already establishes legitimate READY. Repeated replay of the same committed transition must be idempotent.
5. **Transition record ABORTED:** Failed safe, authorization remains `PENDING` unless invalidated. An ABORTED transition holds zero physical authority. It explicitly cannot release ownership, cannot expose READY, and cannot be mistaken for SUCCESSFULLY_FINALIZED. Any stale replay is deterministically rejected because the state has not transitioned.
6. **Durable recovery record consistent:** Normal operation resumes based on record.
7. **Durable recovery record inconsistent:** Must be repaired by converging to the transition record's committed outcome.
8. **Restart reconstruction:** Final state must remain `SUCCESSFULLY_FINALIZED`, `TERMINATED_AND_PROVEN`, `RELEASED`, `READY`, `CONFIRMED` only when the authoritative finalization linearized. No partial authoritative state may exist.

#### 3. `AUTHORITATIVE_RECONCILE_TERMINATION(physical_operation_id, termination_confirmation, expected_termination_authority_epoch)`
Its purpose is ONLY physical-operation reconciliation after the recovery protocol is already `FAILED`.
Required successful transition:
- `physical_operation_state`: `TERMINATION_PENDING` → `TERMINATED_AND_PROVEN`
- `physical_ownership`: `RETAINED` → `RELEASED`
while preserving:
- `transaction_state = FAILED`
- `protocol_state = FAILED`
- `endpoint_state != READY`

It MUST NEVER produce `SUCCESSFULLY_FINALIZED`, `READY`, or `CONFIRMED`. It is an independent authoritative transition, NOT a special case of `AUTHORITATIVE_FINALIZE(recovery_transition, expected_recovery_authorization_epoch)`.

**Crash Semantics (tied explicitly to `authority_transition` record):**
- **Before reconciliation linearization:** Transition is PENDING. Durable reconciliation has NOT committed. Physical ownership remains `RETAINED`. Transaction remains `FAILED`.
- **After reconciliation linearization:** Transition is COMMITTED. `physical_operation_state = TERMINATED_AND_PROVEN`, `physical_ownership = RELEASED`, `transaction_state = FAILED`, `protocol_state = FAILED`, `endpoint_state != READY`.
- **Local UNKNOWN:** Restart MUST consult the authoritative transition record and durable recovery record. It MUST deterministically reconstruct whether reconciliation committed.
- **Restart:** Final state is strictly reconstructed from the exact `physical_operation_id` bound to the transition record.
- **Duplicate replay:** Safely rejected or durably idempotent because the transition record target identity prevents dual-commit.
- **Cross-operation transition identity:** Every case enforces exact `physical_operation_id` matching, so an older protocol's PATH B cannot mutate a newer protocol's state.

**Explicit Linearization Orders:**
The `UnifiedAuthority` MUST explicitly serialize `ACQUIRE_FENCING_EPOCH`, `AUTHORITATIVE_FINALIZE`, and `AUTHORITATIVE_RECONCILE_TERMINATION`. Exactly one authoritative linearization order must exist for conflicting operations.

- **Case A (Termination reconciliation vs newer epoch acquisition):** If `AUTHORITATIVE_RECONCILE_TERMINATION(E1)` linearizes before `ACQUIRE_FENCING_EPOCH(E2)`, ownership is released under E1. If `ACQUIRE_FENCING_EPOCH(E2)` linearizes first, E1 becomes stale, and the E1 termination reconciliation MUST fail deterministically; ownership remains retained until proven under E2.
- **Case B (Recovery finalization vs termination reconciliation):** `AUTHORITATIVE_FINALIZE` is for active protocols; `AUTHORITATIVE_RECONCILE_TERMINATION` is for `FAILED` protocols. They are mutually exclusive by transaction state. If a stale finalization attempt races a reconciliation, the first to linearize transitions the state; the second fails due to state mismatch.
- **Case C (Duplicate termination reconciliation):** The first `AUTHORITATIVE_RECONCILE_TERMINATION` transitions ownership to `RELEASED`. A duplicate reconciliation against the same operation is durably idempotent and safely returns success (or no-op) without altering state.
- **Case D (Termination reconciliation after restart):** A restart has no local protocol object. `AUTHORITATIVE_RECONCILE_TERMINATION` linearizes based solely on the durable physical operation state, releasing ownership without reviving the protocol.
- **Case E (Termination reconciliation using newer termination authority epoch):** `AUTHORITATIVE_RECONCILE_TERMINATION` can use a newer `termination_authority_epoch` (e.g., E2) for an older operation (e.g., dispatched under E1). If E2 is authoritative at linearization, the transition succeeds and releases ownership.

**Inputs (The Complete Identity):**
The immutable transition requests MUST use explicit input contracts. PATH B authority is the durable physical-operation record. PATH A authority is the active recovery authorization.

**Recovery Finalization Request:**
Must include:

- `recovery_id`
- `physical_operation_id`
- `endpoint_id`
- `device_id`
- `lifecycle_generation`
- `operation_fencing_epoch`

**Physical Reconciliation Request:**
Must include:

*(Note: The old `recovery_id` may remain durable historical metadata, but PATH B MUST NOT require the old protocol projection or active recovery authorization.)*

**Execution-Reconciliation Contract (Mechanically Decidable):**
The `AuthoritativeRecoveryRecord` MUST include an explicit execution-reconciliation contract containing at minimum:
- `dispatch_attempt_id`
- `physical_operation_id`
- Executor/driver authority identity
- Execution-channel reference

- Acceptance witness / authoritative acceptance receipt
- Authoritative execution-status source
- Status-query identity
- Status-query result semantics

**Process Restart & Exact Reconciliation:**
If a process crashes and restarts, it MUST reconcile the authoritative recovery record exactly. If local memory conflicts with durable execution evidence, **durable authoritative execution evidence wins.**
For durable `PENDING(E1)` after process restart:
- **CASE A.1 - `ACCEPTED`:** Requires authoritative evidence that the physical dispatch was accepted. New process MUST NOT dispatch a duplicate physical operation. MUST reconcile/observe the existing operation. MUST retain exact immutable identity. MUST obtain authoritative termination evidence through the defined execution authority. MUST NOT declare success from local state alone.
- **CASE A.2 - `NOT_ACCEPTED`:** Requires authoritative evidence that physical dispatch was never accepted. New process MUST NOT pretend physical execution occurred. NO phantom operation is tracked. MAY enter the defined safe deterministic failure/retry path.
- **CASE A.3 - `UNKNOWN`:** Evidence is insufficient to determine acceptance. New process MUST treat physical state as `UNKNOWN`. NO successor physical dispatch is allowed. Fresh fencing and reconciliation is strictly required before new physical dispatch.
- **CASE B - Durable `PENDING(E1)`, Current Epoch `E2`:** New process MUST treat E1 transaction as ineligible for finalization, deterministically mark it `INVALIDATED`, prohibit E1 physical dispatch/finalization, and begin fresh E2 fencing/recovery.
- **CASE C - Durable `SUCCESSFULLY_FINALIZED`:** New process MUST reconstruct READY/CONFIRMED projection. It MUST NEVER replay physical ownership release, rerun finalization side effects, or reopen the transaction.
- **CASE D - Durable `FAILED`:** FAILED semantics preserved. Late callbacks cannot revive it. (`FAILED` != `INVALIDATED`).
- **CASE E - Durable `INVALIDATED`:** INVALIDATED semantics preserved. Old epoch cannot resume it. It MUST NOT silently become `FAILED`.
- **CASE F - Crash during durable commit boundary:**
  - Before durable linearization → authoritative transaction remains `PENDING`.
  - After durable successful linearization → authoritative transaction is `SUCCESSFULLY_FINALIZED`.
  - Process-local projection after restart → reconstructed strictly from durable authority. Do NOT classify an unknown crash point as local `FAILED`.

**Executor Failure Semantics (Explicit Distinctions):**
- **`SUBMISSION_REJECTED_BEFORE_ACCEPTANCE`:** No physical operation was accepted. Process-local physical operation state = `CLEARED`. No final recovery authorization. Protocol becomes `FAILED`. No `READY`. No physical termination callback is expected.
- **`EXECUTION_FAILED_AFTER_ACCEPTANCE`:** Physical operation remains an authoritative operation record. Physical state becomes uncertain/failed according to the established termination rules. **Ownership is NOT cleared until authoritative termination is resolved.** Timeout/late callback semantics continue to apply.
- **`TERMINATION_AUTHORITATIVELY_PROVEN`:** Ownership can be safely released.
- **`TERMINATION_UNRESOLVED`:** Ownership MUST remain retained.

### 10.2 Distinct Finalization and Reconciliation Paths

To ensure `FAILED` protocols do not block physical termination reconciliation, the architecture strictly separates Recovery Finalization from Physical Operation Reconciliation.

#### PATH A — Recovery Finalization (`finalize_recovery_authorization`)
Executed when the durable recovery record indicates the authorization is active/PENDING. A stale or missing local protocol object MUST NOT by itself determine finalization eligibility when durable authority says the recovery is eligible.

```text
Acquire Lock.

// PHASE 1: DURABLE AUTHORITY LOAD
1. Read authoritative durable recovery record (`durable_record`).
2. Validate `durable_record.transaction_state` == `PENDING` AND `durable_record.protocol_state` == `RECOVERY_IN_PROGRESS`.

// PHASE 2: PHYSICAL TERMINATION FACT VALIDATION
3. Match Immutable Operation Identity:
   Validate `authorization_id`, `recovery_id`, `physical_operation_id`, endpoint/device/lifecycle identity against `durable_record`.
   if mismatch:
       Unlock, Reject (Identity mismatch).
4. Validate Epoch Relationship:
   if confirmation.termination_authority_epoch is not the current authoritative hardware epoch:
       Unlock, Reject (Stale or invalid termination authority).
   if confirmation.termination_authority_epoch != durable_record.recovery_authorization_epoch:
       Unlock, Reject (Mismatched recovery authorization epoch. OWNERSHIP RETAINED. NO READY).
5. Validate Driver Provenance & Exact Fact Authentication:
   if confirmation.driver_authority_proof is invalid or does not exactly authenticate TERMINATED_AND_FINAL for this operation:
       Unlock, Reject (Invalid provenance or missing exact fact).
6. Validate Authoritative Termination State:
   if confirmation.termination_state != TERMINATED_AND_FINAL:
       Unlock, Reject (Early callback violation. OWNERSHIP RETAINED).

// PHASE 3: RECOVERY SAFETY EVIDENCE VALIDATION (PRECOMMIT)
7. Verify Safety Evidence:
   if confirmation.safety_evidence_valid != True:
       Unlock, Reject (Endpoint is UNSAFE. OWNERSHIP RETAINED. NO READY).

// PHASE 4: AUTHORIZATION PENDING
8. State is AUTHORIZATION_PENDING(durable_record.recovery_authorization_epoch).

// PHASE 5: AUTHORITATIVE FINALIZATION (Linearization Point)
9. Construct `recovery_transition` encapsulating full identity and prerequisites.
10. Execute token = AUTHORITATIVE_FINALIZE(recovery_transition, expected_recovery_authorization_epoch):
   if token FAILS:
       Unlock, Reject (Epoch changed or commit rejected. NO OWNERSHIP RELEASE. NO READY. NO CONFIRMED).

// PHASE 6: ATOMIC FINAL STATE COMMITTED
10. The commit is successful.
    // Atomically inside DURABLE authority (AuthoritativeRecoveryRecord):
    - transaction_state = SUCCESSFULLY_FINALIZED
    - physical_operation_state = TERMINATED_AND_PROVEN
    - physical_ownership = RELEASED
    - endpoint_state = READY
    - protocol_state = CONFIRMED
    // Local projection is reconstructed strictly from durable authority.
Unlock.
```

#### PATH B — Physical Operation Reconciliation (`reconcile_physical_operation`)
Executed when the recovery protocol has `FAILED` (e.g., due to timeout) but physical ownership is still `RETAINED`.

PATH B MUST NOT depend on an active recovery protocol. It uses the durable authoritative record to identify the physical operation. The original `recovery_id` may remain immutable historical metadata, but reconciliation MUST NOT require the old protocol projection to be active or locally reconstructable.

```text
Acquire Lock.

// PHASE 1: PHYSICAL TERMINATION FACT VALIDATION
1. Match Immutable Operation Identity from Durable Record:
   Validate confirmation against the authoritative reconciliation identity:
   - physical_operation_id
   - endpoint_id
   - device_id
   - lifecycle_generation
   - operation_fencing_epoch
   - termination_authority_epoch
   - driver_authority_proof
   - termination_state
   if identity mismatches:
       Unlock, Reject (Identity mismatch).
2. Validate Epoch Relationship:
   if confirmation.termination_authority_epoch is not the current authoritative hardware epoch:
       Unlock, Reject (Stale or invalid termination authority).
3. Validate Driver Provenance & Exact Fact Authentication:
   if confirmation.driver_authority_proof is invalid or does not exactly authenticate TERMINATED_AND_FINAL for this operation:
       Unlock, Reject (Invalid provenance or missing exact fact).
4. Validate Authoritative Termination State:
   if confirmation.termination_state != TERMINATED_AND_FINAL:
       Unlock, Reject (Early callback violation. OWNERSHIP RETAINED).

// PHASE 2: DURABLE AUTHORITY PRECONDITIONS (EXPECTING FAILURE)
5. Read Durable Authoritative Record:
   if durable.transaction_state != FAILED or durable.physical_operation_state != TERMINATION_PENDING or durable.physical_ownership != RETAINED:
       Unlock, Reject (Not a valid state for physical reconciliation. Protocol might be active, use Path A).

// PHASE 3: AUTHORITATIVE RECONCILIATION (Linearization Point)
6. Execute AUTHORITATIVE_RECONCILE_TERMINATION(physical_operation_id, confirmation, confirmation.termination_authority_epoch):
   if transition FAILS:
       Unlock, Reject (Epoch changed or transition rejected. OWNERSHIP RETAINED).

// PHASE 4: ATOMIC RECONCILIATION COMMITTED
7. The commit is successful.
    // Atomically inside DURABLE authority (AuthoritativeRecoveryRecord):
    - transaction_state = FAILED (immutable)
    - physical_operation_state = TERMINATED_AND_PROVEN
    - physical_ownership = RELEASED
    - endpoint_state != READY (remains QUARANTINED/RECOVERY_REQUIRED, NOT safe)
    - protocol_state = FAILED (immutable, late termination CANNOT revive protocol)
    // Local projection is reconstructed strictly from durable authority.
    // A PATH B cross-epoch termination proof cannot be replayed into PATH A.
Unlock.
```

## 12. Failure Semantics

**Explicit Failure Resolutions:**
1. **Early / Invalid Callback:** Reject callback immediately. Protocol state remains unchanged. Physical ownership remains retained. NO `READY` transition.
2. **Durable Post-Timeout Physical Reconciliation:** A timeout makes the recovery protocol permanently `FAILED`, but the physical operation itself possesses an independent lifecycle (`ACTIVE` → `TERMINATION_PENDING` → `TERMINATED_AND_PROVEN`). 
   - A timeout NEVER revives the protocol.
   - Late physical termination MUST NOT produce `READY` and MUST NOT change `FAILED` to `CONFIRMED`.
   - Late physical termination MAY reconcile durable physical ownership. Ownership is only released AFTER authoritative termination proof. This is independent of reopening the failed recovery protocol.
3. **Executor Failure Semantics (Post-Validation, Pre-Commit):**
   - **`SUBMISSION_REJECTED_BEFORE_ACCEPTANCE`:** Local operation state = `CLEARED`, Protocol → `FAILED`, NO physical termination callback is expected.
   - **`EXECUTION_FAILED_AFTER_ACCEPTANCE`:** Physical dispatch was accepted but execution later fails. Operation record is RETAINED. Ownership is NOT released until authoritative termination is resolved (`TERMINATION_AUTHORITATIVELY_PROVEN`).
   - **Invalid Safety Evidence Before Commit:** Protocol → `FAILED`, physical operation ownership = `RETAINED` (if an operation exists). Effective physical authority depends on epoch validity. NO `READY`, NO ownership release through final commit.
4. **Crash-During-Commit Semantics:**
   - Before durable linearization → authoritative transaction remains `PENDING`.
   - After durable successful linearization → authoritative transaction is `SUCCESSFULLY_FINALIZED`.
   - Process-local projection after restart → reconstructed strictly from durable authority. A crash point is NEVER classified as local `FAILED` merely because it is unknown locally.
