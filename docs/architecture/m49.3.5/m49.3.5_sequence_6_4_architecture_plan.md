# SEQUENCE 6.4 — FINAL ARCHITECTURE AUTHORITY PASS
# INDEPENDENT EPOCH DOMAINS + RECOVERY / RESTART SAFETY

## 0. PURPOSE
This document formally defines the definitive architecture for Sequence 6.4. It explicitly segregates the `controller_epoch` and `device_epoch` domains, stripping all caller-supplied trust in epoch values and defining strict state invariants across controller/device restarts, process boundaries, and failure interleavings.

## 1. PRIMARY ARCHITECTURAL DECISION
The system MUST have independent durable authority domains:
- `ControllerAuthority` owns the `controller_epoch`.
- `DeviceEpochAuthority` owns the `device_epoch` independently for each device.

The architectural invariant is absolute:
`controller_epoch != device_epoch`

These domains may share base abstract implementations, file-locking semantics, or serialization primitives, but they MUST NOT share the same logical epoch counter sequence. A device restart MUST NOT advance the global controller epoch, and a controller restart MUST NOT implicitly advance every device epoch.

## 2. AUTHORITY OWNERSHIP

### Controller Epoch
**Authoritative Owner:** `ControllerAuthorityStore`
**Responsibilities:**
- Allocate controller epochs.
- Durably persist the authoritative controller epoch (e.g., `controller_epoch.json`).
- Provide cross-process exclusive authority.
- Reject stale controller epochs.
- Preserve monotonicity.
- Survive controller process crashes without regression.

### Device Epoch
**Authoritative Owner:** `DeviceEpochAuthority` = sole authoritative device_epoch allocator and validator.
`DurableGlobalCoordinator` = orchestration layer only. The coordinator may request device-epoch operations but must never independently allocate, advance, or validate device epochs as a competing authority.
**Responsibilities:**
- Allocate device epochs independently for each physical device.
- Persist the epoch durably for each device.
- Guarantee monotonicity per device.
- Provide cross-process exclusive authority for that device.
- Reject stale device epochs from mutating state.
- Survive controller/process crashes entirely unaffected.
- Prevent one device's rollover from mutating any other device's epoch.

**Durable Representation:**
Conceptually structured as:
```text
<storage_root>/devices/<device_id>/device_epoch.json
<storage_root>/devices/<device_id>/.device_epoch.lock
```

## 3. REQUIRED DEVICE-EPOCH API SEMANTICS

The `DeviceEpochAuthority` will expose:

1. `read_current_device_epoch(device_id)`
   - **Durability:** Reads from the durable `device_epoch.json`.
   - **Locking:** Unlocked/shared read.
   - **Missing-file behavior:** Fails closed (`PersistenceResourceIntegrityError`) unless called via initialization paths explicitly allowing creation.
   
2. `allocate_next_device_epoch(device_id)`
   - **Durability:** Atomically persists `D_next` (`fsync`). The allocation itself IS a durable commitment.
   - **Locking:** Requires exclusive OS-level per-device file lock.
   - **Monotonicity:** Guarantees strictly monotonic increments per device.
   - **Cross-process:** OS locks enforce deterministic serializability between racing processes.
   - **Rollback:** Final on fsync. Pre-fsync failure implies allocation aborted.

3. `assert_authoritative_device_epoch(device_id, epoch)`
   - **Durability:** Validates against the durable `device_epoch.json`.
   - **Locking:** Acquires exclusive lock briefly to prevent TOC-TOU.
   - **Stale caller:** Raises `PersistenceEpochMismatchError` if epochs differ.

4. `hold_device_epoch_authority(device_id, epoch)`
   - **Locking:** Context manager yielding execution under exclusive lock after asserting authority.
   - **Corruption:** JSON parse errors or EOF raise `PersistenceResourceIntegrityError` (Fail-closed).

## 4. CONTROLLER EPOCH API REMAINS INDEPENDENT
The existing `ControllerAuthorityStore` is untouched. 
`allocate_next_device_epoch(device_id)` MUST NOT invoke `ControllerAuthorityStore.allocate_next_epoch()`. 

A device epoch (e.g., `D17`) and a controller epoch (e.g., `C42`) are strictly disjoint.
The canonical physical identity remains exactly:
`(device_id, device_epoch, controller_epoch, physical_operation_id, command_nonce)`

## 5. DEVICE RESTART / REINITIALIZATION AUTHORITY

The flow fundamentally revokes caller-supplied trust:

```text
DEVICE RESTART DETECTED (caller signals physical drop)
        ↓
DEVICE ENTERS RECOVERY / QUARANTINE
        ↓
OLD DEVICE EPOCH OPERATIONS REMAIN UNRESOLVED
        ↓
FRESH DEVICE READINESS / ISOLATION PROTOCOL
        ↓
DEVICE EPOCH AUTHORITY ALLOCATES D_next (System dictates authority)
        ↓
D_next DURABLY COMMITTED 
        ↓
RUNTIME DEVICE EPOCH PROJECTION
        ↓
ENDPOINT EPOCH SYNCHRONIZATION
        ↓
DEVICE READY
        ↓
PHYSICAL ADMISSION OPENS
```
The caller requests. The authority allocates. 

## 6. CONTROLLER RESTART MUST NOT CHANGE DEVICE EPOCH

**Proof 1: Controller Restart**
When the controller process restarts, `ControllerAuthority` allocates `C2` (where `C2 > C1`).
Because the `DeviceEpochAuthority` is isolated per-device and was not invoked by the controller reboot lifecycle, the device's epoch remains `D1`. 
The rehydration engine uses `C2` as the authoritative writer to flag unresolved ops `(D1, C1)` as `FAULTED_UNKNOWN`. Device D1's durability remains untampered.

**Proof 2: Device Restart**
When a device is explicitly restarted, `DeviceEpochAuthority` allocates `D2` for that device.
Because `ControllerAuthority` was not invoked, the controller epoch remains `C1`.
Future commands to this device are bound to `(device_id, D2, C1)`. The global controller epoch was not mutated.

## 7. CRASH BOUNDARIES FOR DEVICE-EPOCH ALLOCATION

- **D-EPOCH-1 (Before allocation):** No new authoritative device epoch exists. Recovery must restart from old state.
- **D-EPOCH-2 (During allocation before durable persistence):** Fails cleanly. Old epoch remains authoritative. No ambiguous state.
- **D-EPOCH-3 (After durable epoch persistence):** New device epoch is now strictly authoritative. Process crash immediately after leaves the device in the new epoch, but permanently unready (since no readiness commit occurred).
- **D-EPOCH-4 (After epoch allocation but before readiness commit):** Device remains non-READY. Admission remains closed. A subsequent recovery must re-verify hardware and allocate yet another epoch, or explicitly abort.
- **D-EPOCH-5 (Hardware readiness confirmed but DEVICE_READY commit fails):** `DEVICE_READY` is NOT assumed. Admission remains closed. Startup/recovery re-verifies readiness entirely.
- **D-EPOCH-6 (DEVICE_READY durable commit succeeds but runtime projection fails):** Durable state remains authoritative. Process crashes or runtime must explicitly reconcile via journal reconstruction before admission can open. No silent divergence.

## 8. DEVICE-EPOCH JOURNAL / RECORD MODEL
Establishing a new device epoch requires distinct durable records:

1. `DEVICE_EPOCH_ALLOCATED` (or implicit within the atomic `device_epoch.json` allocation).
2. `DEVICE_READY_COMMITTED` (Written to the device journal).

`DEVICE_READY_COMMITTED` must identify:
- `device_id`
- `new_device_epoch` (allocated by `DeviceEpochAuthority`)
- `previous_device_epoch`
- `controller_epoch` (contextual fencing authority representing who authorized the readiness, NOT the allocator of the device epoch)
- `readiness_evidence_identity`
- `timestamp`

They are not merged. The device epoch allocation is a distinct durable commitment from the semantic `DEVICE_READY` hardware proof commitment.

## 9. MIGRATION OF EXISTING DEVICE STATE
**Legacy Shared-Era State:** The repository's existing `epoch_id` in the device journal represents the **legacy shared epoch**.
**Migration Strategy:**
- The system must treat the presence of a legacy shared epoch without an explicitly segregated `device_epoch.json` as requiring explicit migration.
- A `DEVICE_EPOCH_DOMAIN_INITIALIZED` marker (or implicit creation of `device_epoch.json` using the legacy value) occurs strictly on the first safe recovery boot.
- If the history is dangerously ambiguous, it fails closed, requiring explicit operator intervention. Ambiguous history NEVER produces `DEVICE_READY`.

## 10. CANONICAL IDENTITY MIGRATION
Historical operations MUST remain unmutated.
A historical `D1/C1` physical operation record from the legacy era is permanently treated as `D1/C1`. The new segregated authority models strictly evaluate them using their historical identities.

## 11. RESTART RECOVERY FLOW
```text
INITIALIZING
    ↓
allocate / establish new controller authority (C2)
    ↓
load durable session state
    ↓
load durable device authority/state (D1)
    ↓
identify unresolved historical operations (e.g. D1/C1)
    ↓
preserve physical ownership (capacity = preserved)
    ↓
mark unresolved operations FAULTED_UNKNOWN as required
    ↓
reconcile device recovery requirements
    ↓
validate stale authority boundaries
    ↓
start reconciliation safely (TelemetryReconciler enabled)
    ↓
READY (Physical command admission opens, normal execution begins)
```
- **Physical command admission:** Only allowed in `READY`.
- **Telemetry processing:** Only allowed after reconciliation starts safely (post-rehydration).
- **Capacity reconstruction:** Occurs implicitly via "load durable session state" and is preserved by "mark unresolved operations FAULTED_UNKNOWN".

## 12. G13 END-TO-END DESIGN
`E1 telemetry` (C1) arrives after `controller rollover E2` and `E2 rehydration` (which flagged the op as `FAULTED_UNKNOWN`).
- **Result:** `ReconciliationDaemon._resolve_terminal_record()` observes `C1 < C2`.
- It explicitly rejects the update (`StaleEpochError`).
- Rejection is observable (logged/metric incremented).
- The telemetry is recorded in a non-authoritative audit stream or discarded safely.
- No durable terminal mutation occurs.
- No capacity is released.
- E2 recovery state (`FAULTED_UNKNOWN`) is not overwritten.

## 13. FAULTED_UNKNOWN LIFECYCLE
`RUNNING` -> controller crash -> `FAULTED_UNKNOWN` -> `QUARANTINED` / recovery-required.
It requires fresh authoritative physical evidence to yield a legal terminal resolution.
It is explicitly prohibited for `FAULTED_UNKNOWN` to automatically become `COMPLETED`, automatically become safe to retry, or automatically release capacity without hardware proof.

## 14. RECONCILIATION ORDERING
- **During REHYDRATING:** `ReconciliationDaemon` is OFF. Telemetry is queued in transport or dropped. It cannot mutate state.
- **Before READY:** No terminal telemetry can release capacity because reconciliation is not active.
- **After READY:** Telemetry must carry `(C_record >= C_authoritative)`. Old telemetry from an old controller epoch, old device epoch, or old lease generation is strictly rejected by the reconciler.

## 15. LOCKING MODEL

**Deadlock Analysis & Lock Order Hierarchy:**
1. `GLOBAL_TRANSACTION_LOCK` (Topology scope)
2. `CONTROLLER_EPOCH_AUTHORITY_LOCK` (Global Controller scope)
3. `DEVICE_EPOCH_AUTHORITY_LOCK` (Per-Device scope)
4. `GLOBAL_PHYSICAL_ADMISSION_LOCK` (Admission scope)
5. `SESSION_JOURNAL_LOCK` (Per-Session scope)

Strict top-down acquisition guarantees no circular dependencies. Device epoch authority does NOT wrap ordinary command admission (commands use `read_current_device_epoch` locklessly or prior to admission). Device epoch authority locks are explicitly acquired ONLY for device restart, epoch allocation, and readiness commits.

## 16. OLD PROCESS VS NEW DEVICE EPOCH
Old process (D1). New device recovery (D2).
The driver/endpoint boundary requires an explicit epoch match. A D1 physical command submitted to an endpoint fenced to D2 will be synchronously rejected by the endpoint (`DeviceCommandValidationError` / `EpochMismatch`), protecting physical safety while maintaining the historical identity in the legacy process's memory.

## 17. CROSS-PROCESS MODEL
OS-level file locks (`fcntl.flock` or `msvcrt.locking`) strictly enforce serialization:
- P1 and P2 attempt device epoch allocation simultaneously: File lock serializes them. P1 gets D2, P2 gets D3. 
- P1 holds device epoch authority, P2 attempts stale mutation: P2 is locked out or fails the authority assertion upon lock acquisition.
- All cross-process boundaries are purely deterministic. No sleep-based races.
