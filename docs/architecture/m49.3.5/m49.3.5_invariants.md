# M49.3.5 SYSTEM INVARIANTS

## G1: DURABLE CAPACITY RECONSTRUCTION & ATOMIC ADMISSION
- `reserved_capacity == count of durable operations that still require physical execution capacity`.
- Terminal commit and capacity release MUST execute in ONE ATOMIC TRANSACTION.
- `PHYSICALLY_ISOLATED` DOES NOT require physical execution capacity. It releases capacity because the operation is permanently isolated from hardware, while preserving history.

## G3: DISPATCH/CANCEL LINEARIZATION
- `DISPATCHING` means physical execution may have started (Possibility = Unknown/Possible).
- Cancellation locks the row. If `QUEUED`, sets to `ABORTED`. If `DISPATCHING` or `RUNNING`, cancel returns `CANNOT_CANCEL_MUST_RECONCILE`.

## G5: PHYSICAL COMMAND IDEMPOTENCY & EPOCH ENFORCEMENT
- Authoritative physical command identity: `(device_id, device_epoch, controller_epoch, physical_operation_id, command_nonce)`.
- Hardware/driver MUST validate all fields. Old operations under new epochs or new operations under old epochs are physically rejected.

## G7: CALLBACK CONSUMPTION ATOMICITY & REPLAY
- Callback capability consumption must be ATOMIC.
- A replayed callback credential MUST be rejected immediately after consumption. 

## G8: OPERATION-SPECIFIC EVIDENCE FRESHNESS AND BINDING
- Generic `device_status == IDLE` is REJECTED.
- Acceptable evidence MUST bind exactly to: `device_id`, `physical_operation_id`, `device_epoch`, `controller_epoch`, `command_generation`, `evidence_generation`, `query freshness`, and `driver authority`.
- Valid states: `OPERATION_COMPLETED`, `OPERATION_ABORTED_AND_QUIESCENT`, `OPERATION_CONFIRMED_ABSENT`.
- No false termination is possible under the TRUSTED hardware-driver evidence contract.

## G9: FENCING EPOCH ENFORCEMENT & ANTI-REPLAY
- Fencing Handshake requires `FENCING_AUTHORITY`.
- Hardware Fencing Transcript MUST include: `device_id`, `requested_epoch`, `hardware_challenge_nonce`, `current_durable_epoch`, `authorization_purpose`, `requesting_controller_identity`, `freshness / expiry`.
- Hardware rejects: replayed signature, wrong device, wrong epoch, wrong challenge, expired auth, wrong purpose, unknown controller.

## G10: MULTI-PROCESS BOOTSTRAP EXCLUSIVITY
- MULTIPLE CONTROLLER PROCESSES MAY REMAIN ALIVE. EXACTLY ONE EPOCH IS PHYSICALLY AUTHORITATIVE. ONLY THE AUTHORITATIVE EPOCH MAY MUTATE HARDWARE. ALL OLDER EPOCHS ARE PHYSICALLY REJECTED.

## G11: PHYSICAL RESTART/REBOOT TRUTH
- NO SOFTWARE/CONTROLLER RESTART EVENT MAY BE TREATED AS PHYSICAL TERMINATION unless the trusted hardware contract explicitly guarantees it.
- Hardware reboot = PHYSICAL STATE UNKNOWN -> capacity retained -> fresh physical probe mandatory. No termination proof from reboot alone.

## G12: PHYSICAL ISOLATION HANDSHAKE & DEVICE REINITIALIZATION
- `QUARANTINED` -> `ISOLATION_PREPARE` -> hardware isolation command -> `ISOLATION_CONFIRMED` -> atomic DB transaction (`PHYSICALLY_ISOLATED`).
- `PHYSICALLY_ISOLATED` -> `REINITIALIZATION_REQUIRED` -> `REINITIALIZATION_PREPARE` -> hardware reset -> `HARDWARE_READY_CONFIRMED` -> fresh device epoch committed -> `DEVICE_READY`.
- Invariant: DATABASE `DEVICE_READY` => hardware readiness has already been authoritatively confirmed.
