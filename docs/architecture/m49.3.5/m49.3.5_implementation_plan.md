# M49.3.5_IMPLEMENTATION_PLAN_FINAL_REVIEW

## HARDWARE REBOOT & PHYSICAL TRUTH (G1)
Software, controller, or driver restarts DO NOT guarantee physical execution stops.
Hardware reboot DOES NOT automatically guarantee physical execution aborts (actuators may continue).
NO SOFTWARE/CONTROLLER RESTART EVENT MAY BE TREATED AS PHYSICAL TERMINATION unless the trusted hardware contract explicitly guarantees it.
If a restart event does not guarantee quiescence -> PHYSICAL STATE UNKNOWN -> capacity retained -> fresh physical probe mandatory -> abort/isolation required. No termination proof from reboot alone.

## PHYSICAL ISOLATION HANDSHAKE (G2)
`QUARANTINED` -> `ISOLATION_PREPARE` -> hardware isolation command -> `ISOLATION_CONFIRMED` -> atomic DB transaction (state = `PHYSICALLY_ISOLATED`, capacity slot = `NULL`) -> `ISOLATION_ACTIVE`.
Rules:
- No hardware confirmation => no `PHYSICALLY_ISOLATED`, no capacity release.
- Isolation timeout/evidence lost => remain `QUARANTINED`, retain capacity, re-probe/reconfirm.

## OPERATION-SPECIFIC TERMINATION EVIDENCE (G3)
`device_status == IDLE` does NOT equal `TERMINATED_AND_PROVEN`.
Acceptable evidence MUST bind to the exact operation: `OPERATION_COMPLETED`, `OPERATION_ABORTED_AND_QUIESCENT`, `OPERATION_CONFIRMED_ABSENT`.
Generic idle evidence lacking operation binding is REJECTED.

## FENCING CONTROL PLANE & ANTI-REPLAY (G4)
`FENCING_AUTHORITY` Signature Transcript: `device_id`, `requested_epoch`, `hardware_challenge_nonce`, `current_durable_epoch`, `authorization_purpose`, `requesting_controller_identity`, `freshness / expiry`.
Hardware MUST reject replayed signatures, wrong device/epoch/challenge/purpose, or expired authorizations.
Controller authenticates to `FENCING_AUTHORITY` using workload identity (e.g., IAM, SPIFFE). `FENCING_AUTHORITY` verifies controller authorization against RBAC/ACL.

## DEVICE EPOCH ENFORCEMENT (G5)
Authoritative physical command identity: `(device_id, device_epoch, controller_epoch, physical_operation_id, command_nonce)`.
Hardware/driver validates all required fields, strictly rejecting old operations under new device epochs, new operations under old device epochs, etc.

## DEVICE REINITIALIZATION (G6)
`PHYSICALLY_ISOLATED` -> `REINITIALIZATION_REQUIRED` -> `REINITIALIZATION_PREPARE` -> hardware reset/re-enable -> `HARDWARE_READY_CONFIRMED` -> fresh device epoch committed -> `DEVICE_READY`.
Invariant: DATABASE `DEVICE_READY` => hardware readiness has already been authoritatively confirmed.
If crash occurs after `HARDWARE_READY_CONFIRMED` but before DB commit: DB remains `REINITIALIZATION_REQUIRED` -> re-probes hardware readiness on startup.

## CAPACITY_MODEL & PHYSICAL CONSUMPTION
GLOBAL_PHYSICAL_OPERATION_CAPACITY = N.
`reserved_capacity == count of durable operations that still require physical execution capacity`
- `QUEUED`, `DISPATCHING`, `RUNNING`, `RECOVERY_REQUIRED`, `QUARANTINED` -> reserves capacity.
- `PHYSICALLY_ISOLATED` -> DOES NOT require physical execution capacity.

## CRASH_RECONCILIATION & ABORT PROOFS
E2 recovery protocol strictly probes hardware.
If `RUNNING`: Request abort -> obtain abort result -> perform FRESH authoritative status/evidence query -> verify quiescence -> ONLY THEN `TERMINATED_AND_PROVEN`.
If abort returns failure, timeout, UNKNOWN, or ambiguous: NO TERMINAL PROOF, NO CAPACITY RELEASE. State becomes `QUARANTINED` / recovery continues.
